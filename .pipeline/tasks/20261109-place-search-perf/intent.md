# Intent

> 메인 설계 에이전트가 사람과 대화로 작성. 승인 기록은 `approval.json`(`agent-pipeline approve-intent`), 승인 후 이 파일 수정 금지.

## 해결할 문제

- 여행지 검색 1차(PR #280) 운영 실측(2026-11-09, PR #281): 일치 건수가 많은 검색어가 느림
  - '카페'(전국, 일치 25,650건) p50 8,909ms · p95 9,060ms, '카페'(서울 `region=11`) p50 8,636ms
  - 일치가 적은 검색어는 빠름: 막창 177ms, 스타벅스 117ms, 해운대 83ms, 밀본그레이츠 70ms (p50)
- 원인(운영 `EXPLAIN ANALYZE`): FULLTEXT 탐색 단계가 13.5초, 정렬은 수 ms
  - 현재 쿼리는 일치한 행을 전부 읽은 뒤 `active`·지역 필터와 `ORDER BY (정확일치) DESC, id`를 적용 → 비용이 전국 일치 건수에 비례
  - DB VM 메모리 956MB, InnoDB 버퍼 풀 128MB < place 데이터 198MB + 인덱스 250MB, 스왑 756MB 사용 → 행 읽기가 디스크에 묶임
  - 지역 필터를 걸어도 FULLTEXT가 먼저 전국 일치를 만들어서 효과 없음
- 흔한 두 글자 검색어(카페·식당·치킨 등)는 사용자가 가장 먼저 칠 검색어라 9초면 검색 기능을 못 씀

## 의도

- 일치 건수가 많은 검색어도 일치가 적은 검색어와 비슷한 시간에 응답하도록, 검색 비용이 전국 일치 건수에 비례하지 않는 구조로 바꿈
- 구현 방식은 spec 단계에서 로컬 재현 실측으로 비교해 결정(결정 2)

## 포함 범위

1. **로컬 재현**: 운영 규모(약 100만 행)·운영과 같은 작은 버퍼 풀(128MB)로 MySQL에서 느린 검색을 재현하고 후보 방식별로 측정, 수치를 spec에 기록
2. **검색 개선 구현**: spec에서 고른 방식으로 `GET /api/v1/places/search`의 장소 검색 경로 변경
   - 후보 A: 쿼리·인덱스 변경 — 일치 행 전체 정렬을 없애 `LIMIT`에서 일찍 멈춤, 정확 일치는 별도 인덱스 조회 등
   - 후보 B: 앱 메모리 인덱스 — 운영 EC2 t4g.small 2GB, 앱 컨테이너 한도 1.5GiB(적재 중 최대 595MiB 사용)
3. **기존 검색 계약 유지**
   - 검색어는 공백 제거 후 2~50자, 공백 무시 매칭("밀본 그레이츠" = "밀본그레이츠")
   - 정확 일치 이름이 맨 앞, `active` 장소만, 지역 필터는 하위 지역(일반구 포함)까지, `size` 1~50
   - 정확 일치 다음의 결과 순서는 계약이 아님(현재 id 순, 프론트 미연동) → 방식에 따라 바뀔 수 있음
   - 적재(갱신·재매칭·신규·비활성화) 후 검색 결과가 새 상태를 반영

## 제외 범위

- 적재 속도 개선(`rewriteBatchedStatements`, 현재 2시간 57분), 적재 후 스테이징 테이블 비우기 → 별도 S 태스크(결정 1)
- DB 버퍼 풀 확대·DB VM 증설 등 인프라 변경 (결정 2, 운영 DB 설정 변경은 에이전트 금지 작업이기도 함)
- 한 글자 검색, 검색 결과 관련도 순위 개선, 지역 검색(메모리 카탈로그, 이미 빠름)
- 운영 배포 후 지연 실측 → 사람이 실행, 결과는 result에 기록

## 결정 사항 (2026-11-09, 사용자)

1. **범위 = 검색만** — 노션 후속 TODO 중 "검색 성능 개선"과 "두 글자 검색 개선"은 원인이 같아 이 태스크 하나로 처리
   - 기각: 적재 속도·스테이징 비우기 포함 — 분기 1회 백그라운드 작업이고 서비스 영향이 없음, 적재 속도는 운영 적재(3시간)를 다시 돌려야 효과 확인 가능
2. **방식 = spec에서 로컬 재현 실측 후 결정, 인프라 변경 제외** — 쿼리 변경이 목표를 달성하면 서버 메모리를 쓰지 않는 쪽을 우선
   - 기각: 메모리 인덱스로 바로 확정 — 쿼리 변경만으로 될지 확인 전에 EC2 메모리·재로딩 로직 비용을 미리 짐
   - 기각: DB 증설 — DB VM 956MB라 버퍼 풀을 place 크기만큼 못 키움, VM 업그레이드 비용 발생
3. **목표 = 운영 '카페' p95 1초 이하** (전국·지역 필터 모두)
   - 기각: 300ms(자동완성 수준, 지금 요구 없음), 3초(다시 손볼 가능성)

## 성공 기준

- 일치 건수가 많은 검색어의 검색 1회 비용이 일치 건수에 비례하지 않음 — 일치 건수를 10배로 늘려도 검색 1회가 읽는 place 행 수(또는 처리량)가 늘지 않음을 테스트로 고정 (전국·지역 필터 모두)
- 로컬 재현(약 100만 행, 버퍼 풀 128MB)에서 개선 전·후 '카페'류 검색 지연을 측정해 spec·result에 기록, 개선 후 일치가 적은 검색어와 같은 자릿수
- 기존 검색 계약(포함 범위 3) 그대로 통과: 기존 `PlaceSearchDockerTest`·통합 테스트 유지, 적재 후 반영 확인 포함
- 일치가 적은 검색어(희귀어·여러 글자)의 지연이 나빠지지 않음 (로컬 재현 측정)
- 메모리 인덱스를 고른 경우: 기동·적재 후 재로딩, 사용 메모리 측정값을 spec에 기록하고 앱 컨테이너 한도 안에서 동작
- 단위+통합 테스트 포함 `./gradlew test build`(agent-pipeline gate) 통과, `./gradlew dockerTest` 통과
- 배포 후 사람 확인 항목(이 태스크 완료 조건 아님): 운영 '카페' 전국·`region=11` p95 1초 이하, 막창·스타벅스 등 기존 측정 검색어 지연 비악화 → result에 기록
