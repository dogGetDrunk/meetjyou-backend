# Spec critique — round 1

### C-r1-01 The approved service-key environment variable needs an explicit binding contract

- Grounds: `intent.md:22,39,48` requires enabling the integration through `PLACE_TOUR_SERVICE_KEY` while leaving environments without a key disabled. `spec.md:84-89` declares `@ConfigurationProperties` with the property `place.tour.service-key` and names that environment variable, but `spec.md:94-99` contains no configuration mapping or equivalent binding step. Spring Boot's canonical environment-variable spelling for `place.tour.service-key` is `PLACE_TOUR_SERVICEKEY`; `PLACE_TOUR_SERVICE_KEY` is not an interchangeable spelling under configuration-properties binding. AT-003 only specifies the missing-key case (`spec.md:38-41`), and AT-005 does not specify how its key is supplied (`spec.md:55-56`).
- Impact: Supplying the exact variable approved in the intent can leave the key at its empty default and every request at `DISABLED`. Tests that set the property directly or construct the properties object would not detect that failure.
- Suggested fix: Specify how the exact `PLACE_TOUR_SERVICE_KEY` variable populates `place.tour.service-key`, such as an explicit configuration placeholder or equivalent mapping, and include the necessary configuration file in the change list. Add a binding test using that environment-variable name, alongside the absent-variable case. Leave the implementation mechanism to the main designer.

### C-r1-02 Connect and read timeouts do not establish the claimed total delay bound

- Grounds: `spec.md:91-92` sets a one-second connect timeout and a two-second read timeout, then claims the worst search delay is DB search plus less than three seconds. REQ-001 and AT-001 (`spec.md:13-20`) specify timeout translation through `MockRestServiceServer`, but neither an overall request deadline nor a test of the claimed elapsed-time bound. A read timeout generally limits an individual blocked read; a server can keep sending partial data within that interval and extend the complete response beyond three seconds. Connection setup and local processing also prevent deriving a strict total bound from those two settings alone.
- Impact: The spec promises a latency ceiling that its required mechanism does not enforce. A slow upstream response can exceed the stated eight-second frontend timeout even though neither configured timeout fires, preventing the intended degraded search response from reaching the client in time.
- Suggested fix: Have the main designer decide whether a total external-call deadline is required. If so, specify its enforcement, cancellation/resource-release behavior, and a controlled slow-response test that exercises the real HTTP client configuration. Otherwise remove the unsupported worst-case bound and document the actual limits of the connect/read timeouts; the intent itself requires those timeouts but does not require a three-second total deadline.
