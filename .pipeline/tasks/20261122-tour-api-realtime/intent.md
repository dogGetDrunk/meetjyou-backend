# Intent

## 해결할 문제

- 여행지 검색(`GET /places/search`)은 지역과 소상공인 가게만 찾음. 관광지, 문화시설, 레포츠는 검색되지 않음
- ADR-0004(11/12 결정)로 관광공사 데이터는 DB에 저장하지 않고 검색 시점에 실시간 호출하기로 함 → 연동 코드 없음

## 의도

- 같은 검색창(`GET /places/search`) 한 번에 관광공사 키워드 검색(`searchKeyword2`)을 함께 호출해, 응답에 "관광지" 묶음을 추가
- 관광공사가 실패해도 검색은 실패하지 않음: 지역과 가게 결과는 그대로, 관광지 묶음만 비우고 실패 사실을 응답에 표시
- 관광공사 응답은 어디에도 저장하지 않음(ADR-0004)

## 포함 범위

- 관광공사 클라이언트: `searchKeyword2` 호출, 키워드와 지역 필터(법정동 시도, 시군구 코드), 연결과 응답 타임아웃
- 관광지(12), 문화시설(14), 레포츠(28)만 남기기. 숙박, 음식점, 쇼핑 등은 소상공인 데이터로만 다루므로 제외
- 관광공사 장소를 우리 지역 코드(`region`)에 연결해 응답에 지역을 붙이기
- `PlaceSearchResponse` 에 관광지 묶음과 관광공사 조회 성공 여부 필드 추가(기존 필드는 그대로, 추가만)
- 장애 처리: 타임아웃, 오류 응답, 일일 호출 한도 초과(오류 코드 22)일 때 관광지 묶음만 비움
- 외부 호출은 DB 트랜잭션 밖에서 실행(외부 대기 중 DB 커넥션을 잡지 않음)
- 서비스키가 설정되지 않은 환경에서는 관광공사 호출을 건너뜀 → 키 등록 전에 머지되어 운영에 배포돼도 지금과 같은 검색 결과
- 단위 테스트와 통합 테스트(관광공사는 테스트 대역으로 대체)

## 제외 범위

- 모집글, 파티, 여행계획서가 관광공사 장소를 참조하는 구조(출처 + 외부 id, 이름 저장 여부): 공사 문의 답변 후 별도 태스크
- 좌표 반경 조회(`locationBasedList2`), 지역 목록 조회(`areaBasedList2`), 지도 마커 연동
- 검색 결과 캐싱(debounce로 호출 수를 줄이는 것이 전제, 캐싱은 관측 후 검토)
- 프론트 debounce와 최소 글자 수, 관광지 출처 표기 화면("출처 : ⓒ한국관광콘텐츠랩"): 프론트 작업
- 운영 서버에 서비스키 등록(시크릿, 사람 작업), 운영계정 신청과 트래픽 증설 신청
- 소상공인 검색 경로와 성능 특성(`PlaceSearchRepository`) 변경

## 성공 기준

- 키가 있을 때 `GET /places/search?q=경복궁` 응답에 관광지 묶음이 오고, 각 항목에 콘텐츠ID, 이름, 주소, 좌표, 지역이 있음
- `region` 파라미터를 주면 관광지 묶음도 그 지역과 하위 지역 결과만 옴
- 관광공사 타임아웃, 오류, 한도 초과 시 응답은 200이고 지역과 가게 결과는 그대로, 관광지 묶음은 비고 실패 여부 필드가 실패를 나타냄
- 키가 없으면 관광공사를 호출하지 않고, 지역과 가게 결과는 지금과 같음
- 관광공사 호출 중 DB 커넥션을 잡고 있지 않음(테스트로 확인)
- `./gradlew test` 와 `./gradlew build`(detekt, Konsist) 통과

## 결정 필요

- **관광공사 실제 응답 확인 1회**: 포털 Swagger만으로는 두 가지를 확정할 수 없음
  - `searchKeyword2` 가 관광타입(`contentTypeId`) 필터를 받는지(Swagger에는 없음 → 없으면 받은 뒤 거름)
  - 응답의 `lDongRegnCd` + `lDongSignguCd` 가 우리 5자리 법정동 지역 코드와 그대로 맞는지
  - 개발계정 키가 필요함. 에이전트는 시크릿에 접근하지 않으므로, 사람이 로컬 환경 변수 `PLACE_TOUR_SERVICE_KEY` 로 키를 넣어 주면 확인 호출 몇 번(한도 1,000 중)으로 확인. 불가하면 Swagger 기준으로 구현하고 운영 키 등록 후 확인 항목으로 남김
- **프론트와 응답 형식 합의**(노션 244 TODO): 기존 필드는 바꾸지 않고 추가만 하므로 합의 전에 머지해도 앱은 깨지지 않음. 필드 이름과 형식은 합의 결과에 따라 후속 수정 가능

## 요청 원문과 다른 점

- 노션 244 개요의 "좌표 반경, 지역 목록 실시간 호출"은 이번 범위에서 제외(키워드 검색만). 근거: 지도 마커 화면과 연결이 정해지지 않았고, 키워드 검색만으로 검색창 기능이 완결됨
- 요청의 "debounce 전제"는 프론트 작업이므로 백엔드는 구현하지 않음. 기존 최소 2글자 검증은 그대로 적용됨

## 작업 크기

M — 기능 하나(외부 API 연동 + 검색 응답 확장), migration 없음
