# AT-006-1: 락 대기 후 최신 정원 읽기·3→10→3

- 요구사항: REQ-006
- Given:
  - MySQL REPEATABLE READ, Post.capacity=Party.capacity=3, joined=1, PLANNING/OPEN
  - A가 updatePost(capacity=10) 실행 후 파티 락을 보유한 채 커밋 직전 정지
  - B의 RR snapshot은 A 커밋 전 정원=3 관측; 일반 경로와 B에서 Post를 미리 관리 상태로 로드한 변형을 각각 실행
- When:
  - B가 updatePost(capacity=3) 호출, lockPartyOfPost에서 party 행 lock wait 관측
  - 관측 후 A 커밋 허용, B의 party → Post locking read + locked refresh 및 편집 커밋까지 대기
- Then:
  - A·B 모두 성공, deadlock·timeout 없음, B가 실제 대기했음
  - 최종 새 트랜잭션에서 Post.capacity=Party.capacity=3, joined=1
  - 사전 로드 변형도 같은 결과; locking read 제거 및 locked refresh 제거가 각각 실패로 드러나는 oracle
  - stale Post=3을 기준으로 dirty checking하여 Post UPDATE를 생략하고 Party만 3으로 만드는 회귀 검출
- 작성자: 보조 설계
- 코드 작성자: 별도 세션의 Terra
- 보호 대상 테스트 파일:
  - `src/dockerTest/java/com/dogGetDrunk/meetjyou/party/PostLockFreshReadDockerTest.kt`
- 테스트 종류: MySQL dockerTest(Kotest BehaviorSpec, H2 대체 금지)

## 구현·검증 지침
- PostRowLock은 PESSIMISTIC_WRITE query + refresh(post, PESSIMISTIC_WRITE) 양쪽 필요
- SqlPausePoint 또는 latch로 A 커밋을 통제, performance_schema.data_lock_waits로 대상 party 행 대기 확인
