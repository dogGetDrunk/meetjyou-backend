# AT-006-2: 락 대기 중 모집 완료 커밋 이후 재개

- 요구사항: REQ-006, REQ-003
- Given:
  - MySQL REPEATABLE READ, Post.status=RECRUITING/Party.recruitmentStatus=OPEN, progressStatus=PLANNING, joined=1/capacity=4
  - A가 updatePostStatus(RECRUITMENT_COMPLETED)를 실행 후 파티 락 보유·커밋 전 정지
  - B의 RR snapshot은 이전 RECRUITING/OPEN을 관측; 일반 경로와 Post 사전 관리 상태 로드 변형을 각각 실행
- When:
  - B가 updatePostStatus(RECRUITING)를 호출, 해당 party 행 lock wait 관측
  - A 커밋 후 B 잠금 읽기·locked refresh·상태 변경 커밋 허용
- Then:
  - A·B 성공, B 실제 lock wait, deadlock·timeout 없음
  - 최종 새 트랜잭션에서 Post.status=RECRUITING, Party.recruitmentStatus=OPEN, progressStatus=PLANNING
  - stale Post RECRUITING 때문에 UPDATE를 생략하여 RECRUITMENT_COMPLETED/OPEN으로 남는 회귀 검출
  - 사전 로드 변형에서도 같은 결과로 locked refresh 필요성 검증
- 작성자: 보조 설계
- 코드 작성자: 별도 세션의 Terra
- 보호 대상 테스트 파일:
  - `src/dockerTest/java/com/dogGetDrunk/meetjyou/party/PostLockFreshReadDockerTest.kt`
- 테스트 종류: MySQL dockerTest(Kotest BehaviorSpec, H2 대체 금지)

## 구현·검증 지침
- A는 completeParty가 아니라 모집 완료 API/서비스 호출; COMPLETED 거부 시나리오와 구분
- 독립 connection·bounded latch·대상 party 행 lock wait·새 tx 최종 조회, timeout/rollback 원인도 실패 출력
- `./gradlew dockerTest --tests 'com.dogGetDrunk.meetjyou.party.PostLockFreshReadDockerTest'`
