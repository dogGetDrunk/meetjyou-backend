# AT-007-2: 계획서 편집·삭제 교착 방지와 #201 회귀

- 요구사항: REQ-007, REQ-004
- Given:
  - MySQL H 소유 서로 다른 계획서 P0/P1, Post·Party 모두 P0 연결, isPlanPublic=true
  - 시나리오 A: 편집 tx가 party 행 락 보유 후 P1 전환 중 커밋 전 정지
  - 시나리오 B(#201): deletePlan(P0)가 읽기 후 첫 bulk UPDATE 실행 직전 정지, 아직 행 락 미보유
- When:
  - A: deletePlan(P0) 시작, 첫 party detach가 편집의 party 행에서 기다리는 것을 관측 후 편집 커밋
  - B: 정지한 삭제 사이 updatePost(plan=P1,isPlanPublic=true) 편집을 완료·커밋하고 삭제 재개
- Then:
  - 두 시나리오에서 편집·삭제 모두 성공, deadlock·CONCURRENT_REQUEST_CONFLICT·timeout 없음
  - A는 post 행이 아닌 party 행 대기임을 data_lock_waits의 대상 테이블/행·connection으로 확인
  - 새 트랜잭션에서 Post.plan=Party.plan=P1, isPlanPublic=true, P1 존재, P0 및 P0 marker 삭제
  - B의 bulk WHERE plan=P0는 최신 P1 연결을 지우지 않음; #201 기존 결과 유지
  - PartyAggregateDeadlockDockerTest의 나머지 deleteParty ↔ leaveParty 허용 교착 시나리오는 유지
- 작성자: 보조 설계
- 코드 작성자: 별도 세션의 Terra

## 구현·검증 지침
- 기존 plan 시나리오의 post-first 가정·pause point·영어 주석 갱신, SqlPausePoint를 party 락 보유 후 위치에서 사용
- #201 시나리오의 첫 UPDATE 정지 방식은 party-first에서도 유지, 실제 편집 커밋이 삭제 재개보다 앞섰음을 latch로 증명
- `./gradlew dockerTest --tests 'com.dogGetDrunk.meetjyou.party.PartyAggregateDeadlockDockerTest'`

## 개정 (2026-11-02, 메인 설계)
- plan 전환 편집 ↔ deletePlan: 무교착 기대 → accepted deadlock. 한쪽만 PessimisticLockingFailureException, 편집 패배 시 링크 (null, null)·옛 plan 삭제, 삭제 패배 시 새 plan 링크·옛 plan 잔존
- 추가: plan 유지(정원 +1) 편집 ↔ deletePlan → 교착 없음, deletePlan 대기 후 detach, 최종 (null, null, capacity+1)
