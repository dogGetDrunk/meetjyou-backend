# AT-002-2: 축소 거부와 잠금 후 최신 joined 판정

- 요구사항: REQ-002, REQ-004
- Given:
  - 기본: joined=3, Post/Party capacity=5, title=`Old title`, plan=P0, isPlanPublic=true, compPreference=C0
  - MySQL 변형: joined=2/capacity=3, H 포함 JOINED 2명·U의 기존 PENDING 1건; A가 U 승인으로 joined=3을 만들고 파티 락 보유·미커밋
- When:
  - 기본: H가 capacity=2, title=`Rejected title`, 새 일정·Jeju·plan=P1·새 companionSpec 요청
  - MySQL: B는 승인 커밋 전 RR snapshot(이전 joined=2)을 만든 뒤 같은 capacity=2 편집을 시작, party 행 lock wait 확인 후 A 승인 커밋
- Then:
  - 두 변형 모두 PartyCapacityBelowJoinedException, code=PARTY_CAPACITY_BELOW_JOINED, HTTP 409
  - Post/Party 필드·plan·isPlanPublic·compPreference의 편집 변화 없음
  - MySQL에서는 B가 잠금 후 joined=3으로 거부; A 승인은 성공, U=JOINED/party.joined=3 유지, Post/Party capacity=3 유지
  - B의 lock wait는 performance_schema.data_lock_waits에서 실제 관측, stale joined=2를 사용해 축소를 허용하면 실패
- 작성자: 보조 설계
- 코드 작성자: 별도 세션의 Terra
- 보호 대상 테스트 파일:
  - `src/test/java/com/dogGetDrunk/meetjyou/post/UpdatePostPartySyncServiceTest.kt`
  - `src/test/java/com/dogGetDrunk/meetjyou/post/PostPartySyncIntegrationTest.kt`
  - `src/dockerTest/java/com/dogGetDrunk/meetjyou/party/PostLockFreshReadDockerTest.kt`
