# AT-004-1: 완료와 편집의 파티 락 직렬화·문서 정리

- 요구사항: REQ-004, REQ-005
- Given:
  - MySQL PLANNING 파티 joined=1/capacity=4, title=`Old title`, 기존 plan=P0, H 소유 새 plan=P1
  - A의 completeParty가 party 행 락을 잡고 완료 상태를 기록한 뒤 커밋 전 대기
  - 편집 요청의 plan=P1 변경 변형과 plan 변경 없는 변형을 각각 실행
- When:
  - B에서 H의 updatePost(capacity=6, title=`New title`, Jeju, 2030-06-01~06-05 UTC) 시작
  - performance_schema.data_lock_waits에서 B가 해당 party 행에 실제 대기하는 것을 확인 후 A 커밋
- Then:
  - A 완료 성공, B는 락 해제 후 최신 COMPLETED를 읽고 기존 InvalidInputException으로 거부
  - deadlock/CONCURRENT_REQUEST_CONFLICT/lock timeout 없음; 두 변형 모두 같은 순서
  - 새 트랜잭션에서 Party.progressStatus=COMPLETED, recruitmentStatus=CLOSED, Post.status=RECRUITMENT_COMPLETED
  - Post.title=`Old title`, Post·Party capacity=4, 원 일정·Busan·plan=P0·공개 여부·compPreference 유지
  - 기존 deadlock 승패를 허용하던 assertion/KDoc 제거, 새 거부 시나리오로 대체
  - party.md Locked today 확장·해당 Accepted deadlocks 항목 제거·deletePlan 괄호와 Pinned by 정리, post-plan.md updatePost 락 및 party-before-post 설명 diff 존재
