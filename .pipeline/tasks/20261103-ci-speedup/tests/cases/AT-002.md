# AT-002: JVM 단일 MySQL·빈 database 격리·락 대기 귀속 보존

- 요구사항: REQ-002
- Given: Docker daemon 및 기존 dockerTest 실행 환경, SharedMySql 지원 코드와 순차 스펙 실행
- When: `SharedMySql.newDatabase()` 반복 호출 및 마이그레이션·행 락 대기 발생
- Then: 같은 호스트·포트의 서로 다른 빈 database, 마이그레이션 영향 격리, 자기 database의 실제 락 대기만 검출
- 작성자: 보조 설계
- 코드 작성자: 별도 test-writer 세션
- 보호 대상 테스트 파일:
  - `src/dockerTest/java/com/dogGetDrunk/meetjyou/support/SharedMySqlDockerTest.kt`

## 사례 1 — 컨테이너 공유 및 database별 빈 초기 상태

- Given: 테스트 JVM에서 SharedMySql 지원 코드를 사용하는 상태
- When: `newDatabase()`를 두 번 호출하여 X·Y 접속 정보로 각각 연결
- Then:
  - X·Y jdbcUrl의 호스트·포트 동일, 선택 database 이름 상이
  - 각 접속으로 조회한 현재 database가 자기 jdbcUrl의 database와 일치
  - X·Y 모두 자기 database의 테이블 수 0, 시스템 스키마 테이블 제외
  - username·password 접속 정보로 실제 연결 성공
- 반환 타입명·추가 필드명 고정 금지; jdbcUrl에서 호스트·포트·database를 확인하여 불필요한 production API 확장 방지

## 사례 2 — 한쪽 Flyway 마이그레이션의 독립성

- Given: 서로 다른 빈 X·Y database, 기존 dockerTest와 동일한 프로젝트 Flyway 마이그레이션 리소스
- When: X에만 Flyway 마이그레이션 적용
- Then: X 마이그레이션 성공 및 테이블 생성, Y의 자기 database 테이블 수는 여전히 0
- DB 이름만 다른 같은 물리 database 또는 전체 서버 테이블 수를 비교하는 잘못된 검증 금지
- 마이그레이션 이후 정리용 TRUNCATE·공유 컨테이너 stop으로 격리 결과를 만들지 않음

## 사례 3 — 실제 행 락 대기의 database 귀속

- Given: X·Y의 독립 접속 정보, X에 테스트용 행·테이블 준비 및 트랜잭션 A의 행 락 획득
- When: X의 별도 커넥션·트랜잭션 B가 같은 행의 쓰기 락을 요청하여 실제 대기
- Then:
  - 제한 시간 내 X의 `countLockWaits()` ≥ 1 검출, 같은 대기가 지속되는 동안 Y의 `countLockWaits()` = 0
  - X는 실제 대기를 놓치지 않고, Y는 다른 database 대기를 오검출하지 않음
- 대기 감지: `performance_schema.data_lock_waits`의 요청 락을 `data_locks`와 조인하여 `OBJECT_SCHEMA`로 귀속
- `information_schema.innodb_trx.trx_state`·고정 sleep만으로 대기 판별 금지; 유한 timeout 및 완료 동기화로 행 락 대기 성립 보장
- finally에서 A의 락 해제, B 완료 확인 및 모든 커넥션·executor 종료; 실패 시에도 공유 컨테이너 stop 금지
- 자기 database 귀속이 불가능하면 단언 완화·전역 상태 초기화·시나리오 변경 대신 escalation

## 기존 스펙 보존 및 구조 검토

- Given: 기존 17개 스펙·49개 테스트와 위 SharedMySqlDockerTest 추가
- When: `./gradlew dockerTest` 실행 및 변경 diff 검토
- Then:
  - 기존 스펙·테스트 수·시나리오·단언·상수 값 보존, 기존 49개와 신규 보호 테스트 전부 성공, skip 0
  - 새 보호 스펙의 테스트 수는 실제 실행에서 별도 집계, 기존 49개 감소를 신규 테스트 증가로 상쇄 금지
  - 컨테이너 생성 대상 기존 16개 모두 공유 지원으로 교체, 비대상 기존 스펙 임의 변경 없음
  - `MySQLContainer(` 생성 호출 및 이미지 태그 `mysql:8.0.41` 상수는 SharedMySql.kt에만 존재
  - 공유 컨테이너는 JVM당 1개 지연 기동, max_connections >151, 스펙의 공유 컨테이너 stop 없음
  - Spring `@DynamicPropertySource`, 비 Spring Flyway·DriverManager 모두 스펙별 database 사용
  - 전역 락 카운트 대상 6개 스펙은 접속 정보의 `countLockWaits()` 호출, SharedMySql.kt 밖 전역 카운트 없음
  - JdbcSessionStateRoundTripDockerTest의 SELECT_DIGESTS는 `SCHEMA_NAME`으로 자기 database만 조회
  - PartyAggregateDeadlockDockerTest의 `SHOW ENGINE INNODB STATUS`는 기존 진단 로그 유지
  - 병렬 실행 설정·maxParallelForks·컨텍스트 통합·TRUNCATE 공유 스키마 도입 없음
- 기존 16개 파일의 정확한 목록은 설계 입력 미제공; 구현자는 touches인 `src/dockerTest/` 안에서 기존 코드 확인 후 변경 목록·전후 테스트 총량 보고
- 구조 검토와 전체 회귀 실행은 보호 테스트 3사례만으로 대체 불가

## 테스트 형식 (메인 설계 보완, 2026-11-04)

- 기존 dockerTest와 같은 Kotest `BehaviorSpec` + 한국어 Given/When/Then 이름 (예: `UserEmailNotUniqueDockerTest`), `io.kotest.matchers` 단언 사용
- JUnit `@Test`·`org.junit.jupiter.api.Assertions` 금지 — 저장소 테스트 전부 Kotest, Jupiter 테스트 0개라 실행 경로·관례 이탈
- 락 대기 감지는 `Thread.yield()` 바쁜 루프 대신 짧은 간격(예: 50ms) 폴링 + 유한 deadline, 기존 dockerTest 락 대기 폴링과 같은 방식
