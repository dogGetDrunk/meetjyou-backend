# AT-003-2: 수신자·payload 동등성과 실제 preference SELECT 수

- 요구사항: REQ-003, REQ-004
- Given:
  - 실제 JPA·outbox 통합, 공지와 이전 버전 대체 약관 각각 존재, 발송 scheduler/FCM은 기존 테스트 방식으로 격리
  - AT-003-1의 수신자 행렬을 실제 User·preference row로 저장, 각 후보는 겹치지 않는 uuid/id 사용
  - 해당 타입 false·다른 타입 false·row 없음·enabled true·notified false·NORMAL 외 상태 구분
  - 후보 1명·다수의 별도 fixture commit/flush/clear, SQL collector를 발송 호출 직전 초기화
- When:
  - 일반 공지와 약관 원 발송을 각각 실제 발송 경로로 실행, 대상 prefix outbox를 새 tx에서 조회
  - 각 종류에서 후보 1명·10명일 때 user_notification_preference 대상 SELECT만 측정
  - critical 공지를 별도 fixture로 발송; 필요시 실제 생성/발행 API로 AFTER_COMMIT 경유
- Then:
  - 일반 공지·약관의 설정 SELECT는 후보 1명·10명 모두 정확히 1회, critical은 0회 허용·최대 1회
  - 요청 종류별 기대 수신자 집합과 outbox recipient 집합 정확히 동일, 비NORMAL/notified=false 제외
  - 같은 타입 false 제외·다른 타입 false/row 없음 수신·critical의 설정 무시 유지
  - outbox title/body/dataJson/dedupKey는 변경 전 핸들러 원문에서 기대 문자열·JSON 값을 확정해 전체 검증(새 구현의 getter로 기대값 생성 금지), notice:<uuid>:·terms_reconsent:<uuid>: 접두 및 수신자별 키 보존
  - fixture·검증용 SQL은 측정에서 제외, 전체 API SQL 수는 고정하지 않음
- 작성자: 보조 설계
- 코드 작성자: 별도 test-writer 세션
