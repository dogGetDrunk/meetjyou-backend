# AT-005-4: 원 발송 AFTER_COMMIT 중 재발송의 중복 차단

- 요구사항: REQ-005
- Given:
  - 실제 MySQL Testcontainers·Flyway, 실제 두 API 경로, 테스트 본문 트랜잭션 없음
  - 공지와 적격 약관을 각각 독립 시나리오로 실행, 원천 row 커밋·outbox 0건, 정상 수신자 2명 이상
  - 실제 요청을 별도 executor에서 병행, 테스트 관측용 DB 접속과 AFTER_COMMIT의 원/발송 tx가 함께 진행 가능한 pool
  - SqlPausePoint로 선행 발송의 원천 PESSIMISTIC_WRITE 취득 후 첫 outbox insert 직전 정지
  - 경쟁 요청이 같은 원천 row 잠금을 기다림을 performance_schema.data_lock_waits와 관련 lock 정보로 제한 시간 내 폴링 확인
  - 고정 sleep·information_schema.innodb_trx.trx_state로 대기 추정 금지, finally에서 pause·executor·요청 모두 해제
- When:
  - 공지: 실제 관리자 공지 생성 API → 원 tx commit → 실제 AFTER_COMMIT 원 발송이 잠금 취득 후 insert 직전 pause
  - 원천 uuid는 테스트에서 관측한 커밋 row로 확인, 같은 uuid의 관리자 재발송을 시작해 원천 lock wait 관측 후 release
  - 약관: 실제 새 버전 발행 API와 실제 TermsReconsentEventHandler를 통해 같은 순서 수행
  - 핸들러 직접 호출·비트랜잭션 이벤트 발행·테스트 자동 rollback으로 원 발송 대체 금지
- Then:
  - 공지 생성·약관 발행 원 API는 각각 정상 성공, 경쟁 재발송은 지정 409 BROADCAST_ALREADY_SENT 또는 CONCURRENT_REQUEST_CONFLICT
  - 각 원천 row 커밋 유지, 각 prefix outbox는 전체 수신자 1세트만 존재, 사용자별 dedupKey 중복 0
  - 공지·약관 두 경로의 실제 AFTER_COMMIT와 원천 잠금 대기 모두 입증
  - 선행 발송 실패 후 대기 재발송 복구의 추가 경쟁 시나리오는 범위 제외(C-r1-06 결정)
- 계약: 발송 빈·Repository·예외·핸들러·재발송 서비스 시그니처와 테스트 지원 계약은 티켓 T-04 `## 확정 인터페이스` 절을 그대로 따름 — 임의 이름·생성자 금지
