### C-r1-01 약관 재발송의 현재 유효 시점 검사 누락

- 중요도: blocking / REQ-005 / AT-005-2
- 근거: intent 포함 범위의 "이전 버전을 대체한 현재 유효 약관만 허용", 프로젝트 terms 규칙의 `ACTIVE && effectiveAt <= now`; spec REQ-005의 허용 조건은 `ACTIVE`와 같은 type의 `INACTIVE` 존재만 명시
- 반례: 이전 INACTIVE 버전이 있고 새 버전의 status가 ACTIVE이나 effectiveAt이 미래인 상태에서 재발송 요청 → 현 spec 조건으로 허용, 승인된 현재 유효 약관 조건 위반
- 수정 제안: `effectiveAt <= now` 포함, 같은 type의 이전 버전 판단 기준 명시; 대상 잠금 후 같은 발송 트랜잭션에서 적격성 판정과 outbox 저장 수행 명시
- 검증 보강: 미래 시점·정확히 유효 시점·이미 지난 시점, DRAFT·INACTIVE·첫 버전 각각의 결과 고정; 미래 ACTIVE 요청은 409 `TERMS_RECONSENT_NOT_APPLICABLE`, outbox 0건
- 범위 경계: 프로젝트에 이미 기록된 약관 발행 시 이전 버전 조기 INACTIVE 문제의 별도 수정 요구 없음

### C-r1-02 실패 통보 중 예외가 발행 API로 재전파될 수 있는 계약 공백

- 중요도: blocking / REQ-004 / AT-004-1·AT-004-2
- 근거: intent의 "발행 API는 정상 응답", spec의 발송 빈 호출 try/catch 후 `DiscordAlertService.sendOperationalAlert` 실행; 알림 호출 자체의 실패 처리 조건 부재
- 반례: 발송 트랜잭션 실패를 catch한 뒤 운영 알림 전송도 실패 → 알림 호출이 예외를 전파하는 구현이라면 AFTER_COMMIT 핸들러를 통해 원 요청 실패 재발
- 증거 한계: 입력 문서에 DiscordAlertService의 예외 비전파 보장 없음; 해당 서비스의 실제 결함 주장 아님
- 수정 제안: 발송 예외와 운영 알림 예외 모두 발행 요청으로 비전파되는 계약 명시; 기존 서비스가 이를 보장하면 구현 재사용과 검증 근거 기록, 미보장 시 핸들러의 별도 예외 격리
- 검증 보강: outbox 저장 실패와 운영 알림 호출 실패를 함께 주입해 원천 row 커밋·발행 성공·outbox 0건·발송 실패 ERROR 로그 확인; 알림 성공 경로는 기존처럼 1회 호출 확인
- 트레이드오프: Discord 장애 시 실제 알림 도착 보장은 불가하므로 "호출 시도 및 실패 로그"와 "알림 전송 성공"의 수용 조건 분리; 재시도 큐 추가는 이번 범위에서 제외

### C-r1-03 실제 커밋과 일부 저장 이후 실패를 검증하는 테스트 조건 부족

- 중요도: blocking / REQ-004 / AT-004-1·AT-004-2
- 근거: intent에서 AFTER_COMMIT 예외 전파를 미검증으로 표기; spec은 "outbox 저장 실패 주입"만 명시
- 허위 통과 가능성: 핸들러 직접 호출, 자동 롤백되는 테스트 트랜잭션, 첫 insert 전 실패만으로는 실제 발행 요청의 afterCommit 예외 격리 및 이미 저장된 outbox 전량 롤백 입증 불가
- 수정 제안: 실제 공지 생성·약관 발행 API의 원 트랜잭션 커밋을 거치는 통합 테스트 명시; 수신자 2명 이상 중 첫 outbox insert가 flush된 뒤 후속 저장 실패 주입
- 검증 보강: 원천 row는 별도 새 트랜잭션에서 존재 확인, 해당 dedup 접두 outbox는 0건, HTTP 성공·ERROR 로그·운영 알림 1회 확인; 발송 빈 프록시의 트랜잭션 종료 시점 예외도 핸들러의 catch 범위에 포함되는 검증 추가
- 범위 경계: AFTER_COMMIT의 메모리 이벤트 유실 창은 기존 notification 규칙의 수용 위험 유지; durable event 도입 요구 없음

### C-r1-04 게시글 조회의 트랜잭션 범위와 DTO 생성 시점 구체화 필요

- 중요도: major / REQ-002 / AT-002-1·AT-002-2·AT-002-3
- 근거: spec은 트랜잭션 없는 조정 메서드와 readOnly 읽기 부분 제시, `incrementIfEligible`의 REQUIRED 합류도 명시; 클래스 수준 트랜잭션·상위 호출 트랜잭션·읽기 완료 산출물의 경계 미정
- 위험: 읽기에서 엔티티만 반환해 조정 메서드에서 연관 객체를 DTO로 변환하면 읽기 트랜잭션 밖 lazy 접근 가능; 상위 트랜잭션에 조회수 증가가 합류하면 예외를 catch해도 rollback-only가 남아 응답 정상 보장과 충돌 가능
- 수정 제안: 조회·권한 확인·필요한 연관 조회·응답 DTO `.of()`까지 readOnly 경계 안에서 완료, 증가 전 views를 가진 DTO 반환 후 조회수 증가 순서 명시; 조정 메서드의 실제 호출 경로에서 바깥 트랜잭션이 없는 조건과 클래스 수준 설정 처리 명시
- 결정 요청: 상위 트랜잭션 호출을 지원할지 또는 현 API 호출 경로에 계약을 한정할지 메인 설계 결정; 지원 시 실패 비전파와 동시 커넥션 조건을 함께 만족하는 경계 선택 필요
- 검증 보강: 풀 1개 테스트를 실제 상세 조회·DTO 변환·조회수 커밋까지 수행, 트랜잭션이 걸린 테스트 본문으로 요청을 감싸지 않는 조건 명시; 실패 테스트는 단순 mock 예외 외 실제 증가 트랜잭션 롤백 후 정상 응답 확인 포함

### C-r1-05 Repository 호출 횟수만으로 SQL 고정 횟수 입증 불가

- 중요도: major / REQ-001·REQ-003 / AT-001-1·AT-001-2·AT-003-1·AT-003-2
- 근거: intent 성공 기준은 쿼리 횟수 고정; spec의 횟수 검증은 단위 테스트, 통합 테스트는 값·수신자 일치 중심
- 위험: mock Repository 1회 호출은 메서드 내부·연관 지연 로딩의 SQL 증가를 검출하지 못함; 통합 테스트 값이 맞아도 성능 목표 미충족 가능
- 수정 제안: 단위 호출 횟수 검증 유지와 함께 실제 SQL을 세는 통합 검증 명시; fixture 저장·flush·영속성 컨텍스트 clear 후 측정 시작, 캐시·fixture SQL 제외
- 검증 보강: 방 0개는 집계 SQL 0회, 방 1개·10개는 1회; 일반 공지·약관 각각 수신 후보 1명·다수에서 설정 SELECT 1회, critical 공지 0회 허용; 수신자별 preference SELECT가 없는지도 확인
- 트레이드오프: 전체 API의 모든 SQL 횟수 고정 대신 해당 집계·설정 SELECT만 식별하여 검증; 범위 밖 조회나 타이밍에 대한 취약한 단언 방지

### C-r1-06 두 발송 경로의 동시성 및 오류 수용 기준 매핑 누락

- 중요도: blocking / REQ-004·REQ-005 / AT-005-1~AT-005-4
- 근거: AT-005-3·AT-005-4에 공지·약관 각각의 실행 의무 미명시; 404와 약관 비관리자 403은 요구사항에는 있으나 테스트 ID 설명에서 매핑 불명확
- 위험: 한 Broadcaster만 MySQL 동시성 검증을 통과해도 전체 완료로 판정 가능; 유사 구조의 다른 구현에서 잠금·권한 누락을 놓칠 가능성
- 수정 제안: 공지/약관 × 재발송/재발송·원 발송/재발송의 4개 동시성 시나리오를 두 AT에 명시; API별 404·403·성공 recipientCount·409·outbox 불변 조건 매핑 추가
- 검증 보강: 원 발송은 실제 AFTER_COMMIT 핸들러 경유, 첫 트랜잭션의 원천 row 잠금 획득 이후 outbox insert 직전 정지; 경쟁 요청의 실제 잠금 대기는 `performance_schema.data_lock_waits`로 확인, 고정 sleep 사용 금지
- 결과 기준: 성공 경쟁은 1회만 전체 수신자 outbox 생성, 나머지는 지정된 409; 선행 발송 실패·롤백 후 대기 중 재발송이 전체를 복구하는 시나리오도 포함
- 트레이드오프: 새로운 동시성 제어 도입 없이 spec의 원천 row 잠금과 단일 트랜잭션이 실제 MySQL에서 동작하는지 검증

### C-r1-07 채팅방 집계의 JOINED 멤버십 조인과 기존 결과 동등성 근거 부족

- 중요도: major / REQ-001 / AT-001-2
- 근거: intent는 전달된 방들의 기존 unread 결과 유지 요구; spec 신규 쿼리는 요청자 UserParty의 JOINED 조건을 추가; chat 규칙은 ChatParticipant 입장·제거를 수동 동기화로 설명
- 확인 필요: 목록에 포함되는 모든 방에 대해 요청자의 JOINED UserParty가 반드시 존재하는지 입력 문서만으로 입증 불가; ChatParticipant와 UserParty의 관계 불변식·변경 순서도 미제공
- 반례 후보: 목록에 포함되지만 JOINED UserParty가 없는 방이 허용되는 경우 신규 INNER JOIN은 기존 메시지 카운트를 0으로 바꿀 가능성; 실제 발생 여부는 소스 검증 필요
- 수정 제안: 메인 설계가 목록 대상과 멤버십 불변식을 허용된 소스 근거로 확인하고 기록; 보장되지 않으면 실제 목록 선택 규칙과 동등한 집계 조건 확정
- 검증 보강: 다중 방의 서로 다른 lastReadMessageId, 요청자·타인 멤버십, 자기 메시지, 빈 방, 읽음 커서 없음, 전달된 roomUuids 밖의 방 포함 데이터로 정확한 값 단언; JOINED가 아닌 멤버십의 목록 포함 여부에 맞춘 회귀 사례 추가
- 범위 경계: 접근 권한 정책 확대·기존 멤버십 데이터 정리 요구 없음; 현재 결과 보존을 위한 설계 근거 요청

### C-r1-08 dockerTest 완료 기준과 제공된 자동 gate의 불일치

- 중요도: blocking / REQ-004·REQ-005 / intent 성공 기준 및 AT-005-3·AT-005-4
- 근거: intent 완료 기준은 `test`·`build`·`dockerTest` 통과; 지시서 gate와 `.pipeline/project.yaml`은 `./gradlew test build`만 포함
- 증거 한계: `.pipeline/README.md`에는 기존 CI의 dockerTest 언급이 있으나 이 checkout의 CI 실행 조건·같은 HEAD에서 실제 수행 여부는 입력 근거만으로 확인 불가
- 위험: 기본 gate 통과만으로 MySQL 경쟁 테스트와 V43 migration 검증을 완료했다고 오인할 가능성
- 수정 제안: 제공 gate 임의 변경 없이 티켓 검증 명령과 완료 증거에 `./gradlew dockerTest` 의무를 명시; CI가 보장한다면 동일 검증 SHA의 실제 dockerTest 실행·통과 근거를 필수화
- 검증 보강: MySQL/Flyway 경로로 V43 적용·인덱스 존재 확인 포함; H2 create-drop이나 mock Repository 검증은 migration 증거로 대체 불가; Docker 미가동·테스트 미실행은 통과 처리 금지
- 트레이드오프: 공통 엔진·정책 분기나 운영 DB 접근 추가 없이 태스크에 이미 승인된 검증 범위만 보장
