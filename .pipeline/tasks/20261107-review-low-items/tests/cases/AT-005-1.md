# AT-005-1: 마커 교체가 plan 행 잠금을 기다린 뒤 최신 커밋 기준으로 교체 (실제 MySQL)

- 요구사항: REQ-005
- Given: `src/dockerTest` `@DataJpaTest` + 실제 MySQL(`SharedMySql`), `@Transactional(propagation = NOT_SUPPORTED)`. 실제 `MarkerRepository`·`PlanRepository`로 `MarkerService`를 손으로 조립(`CurrentUserProvider`는 mockk, `uuid` = plan 소유자; `PlanAccessGuard` relaxed mockk). 소유자 유저·plan 1개·초기 마커 집합 W(2개) 시드 커밋
- When:
  1. 보유 트랜잭션(별도 스레드, `TransactionTemplate`): plan 행 `SELECT ... FOR UPDATE`(native) → 그 plan의 마커를 삭제하고 집합 X(3개, place 접두 `X-`) 삽입·flush, 커밋하지 않고 대기
  2. 다른 스레드: `markerService.replaceMarkers(planUuid, Y)`(Y = 2개, place 접두 `Y-`)
  3. `performance_schema.data_lock_waits`에서 대기 행이 보일 때까지 폴링(제한 시간 내) — `information_schema.innodb_trx.trx_state` 사용 금지
  4. 보유 트랜잭션 커밋, 2의 스레드 종료 대기
- Then:
  - 3에서 잠금 대기 관측됨
  - 2가 예외 없이 끝남, 반환 목록 = Y
  - 새 트랜잭션에서 조회한 그 plan의 마커 = Y와 개수·place·dayNum·idx 정확히 일치, `X-`·W 잔존 0
- 작성자: 보조 설계
- 코드 작성자: 별도 test-writer 세션
- 기준 실행: red
- 보호 대상 테스트 파일:
  - `src/dockerTest/java/com/dogGetDrunk/meetjyou/plan/MarkerReplaceLockDockerTest.kt`

## 회귀·증거

- base RED: plan 잠금 없음 → 요청이 스냅샷의 W를 지우려다 실패하거나 X가 남음(최종 ≠ Y). 잠금 앞에 일반 조회를 끼운 회귀도 같은 이유로 실패(C-r1-08)
