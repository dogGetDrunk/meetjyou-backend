# Intent

> 메인 설계 에이전트가 사람과 대화로 작성.
> 승인 기록은 `approval.json`(`agent-pipeline approve-intent`), 승인 후 이 파일 수정 금지.

## 해결할 문제

- 2026-10-26 코드 리뷰 Low 지적(#231) 16건 중 미처리 항목. 2026-11-07 최신 코드(`d500baa`) 재확인 결과 15건 잔존, 1건 해소
  - 해소: `removeParticipant`의 세션 끊기 — 이미 `ChatSessionRevocationListener`(AFTER_COMMIT)로 커밋 후 실행
- 잔존 15건 중 아래 7건만 이번 범위. 기준 = 경합 없이도 발생(결정적)하거나, 한 번 발생하면 사람이 손대기 전까지 계속되거나, 고치는 비용이 작은 것
  1. **공개 GET에 만료·무효 토큰** → 401. 로그인 없이 쓰는 API(`versions/check|latest`, `notices/**`, `terms/**`, 닉네임 중복)에 앱이 남은 만료 토큰을 붙이면 거절됨 — 경합 불필요, 앱 실행 시 버전 확인이 실패할 수 있음
  2. **JWT `userUuid` 클레임이 UUID 형식 아님** → `UUID.fromString` 예외로 500 (서명 키가 있어야 만들 수 있어 방어 차원)
  3. **예약 작업(`@Scheduled`) 실패가 조용함** → 오류 로그 파일에만 남고 Discord 알림 없음. 탈퇴 정리(`WithdrawnUserPurgeService.purge`)는 전원 단일 트랜잭션이라 한 명 실패 시 그날 전원 롤백 + 매일 같은 실패 반복을 아무도 모름
  4. **FCM 호출 타임아웃 없음** → `FirebaseOptions` 기본값 0(무한) 확인(firebase-admin 9.5.0 바이트코드). 스케줄러 스레드가 1개(Spring 기본값, 별도 설정 없음)라 응답 없는 FCM 호출 하나가 알림 발송뿐 아니라 탈퇴 정리·조회 로그 정리 등 예약 작업 전부를 멈춤. 또 발송 루프의 catch 안 `recordRetry`가 예외를 던지면 남은 배치와 무효 토큰 비활성화를 건너뜀
     - 리뷰의 "다중 인스턴스 중복 발송"은 현재 단일 인스턴스 + `fixedDelay`라 발생 불가 → 실제 영향은 위 "전체 예약 작업 정지"로 정정
  5. **여행 계획 마커 동시 저장 시 중복** → `replaceMarkers`가 plan 행 잠금 없이 삭제 후 삽입. 저장 버튼 연타로도 가능하고, 오류 없이 데이터가 망가져 409 사후 처리 규칙(CLAUDE.md 동시성 규칙) 대상이 아님
  6. **앱 버전 캐시 stale** → 쓰기 트랜잭션 커밋 전에 캐시를 지우고 `getOrPut`이 원자적이지 않아, 겹친 `/check`가 이전 값을 다시 채우면 다음 쓰기·재시작까지 유지. 강제 업데이트 등록이 반영 안 될 수 있음
  7. **미사용 public 메서드 정리** → src/main 호출 0건 13개 (그중 `PartyRepository.findAllByPlan_Uuid`, `UserPartyRepository.findAllByUser_Uuid`는 테스트에서만 사용)

## 의도

- 결정적으로 나는 오류와 "조용히 계속되는 실패"를 없앰. 드문 경합은 기존 원칙대로 사후 처리·보류
- 개별 땜질보다 공통 확장점에서 해결 (예: 예약 작업 실패 알림은 스케줄러 공통 오류 처리에서 한 번에)

## 포함 범위

- 위 1~7
- 3: 모든 `@Scheduled` 작업의 예외를 Discord 운영 알림으로 보냄. 탈퇴 정리의 단일 트랜잭션 구조는 유지
- 4: FCM 연결·읽기 타임아웃 설정 + catch 안 기록 실패가 남은 배치 처리를 끊지 않게 함
- 5: 같은 plan의 마커 교체 요청을 직렬화(plan 행 잠금)
- 7: 메서드 삭제와 그 메서드만 쓰던 테스트 정리

## 제외 범위

- **알림센터 받은 신청 읽음 범위**(`markReceivedApplicationsRead`가 조회 이후 도착분까지 읽음 처리) — 기획 확인 필요, 노션 보드 TODO로 유지
- **조회수 동일 유저 동시 조회 +2, 로그 정리 10분당 1000건 상한** — 영향이 조회수 1 차이, 상한 초과(시간당 6,000건 이상 조회) 관측 없음
- **게시글 작성·수정 중 plan 동시 삭제 → FK 500** — 본인 plan을 본인이 동시에 지우는 부자연스러운 겹침, 500 + 알림으로 빈도 관측
- **WebSocket connect 리스너 예외 rethrow** — Spring이 이벤트 발행 예외를 로그만 남기고 삼키는 것으로 보여 영향 범위부터 따로 확인 필요
- **채팅 읽음 커서(메시지 id 커밋 순서 역전)** — 드문 경합, 고치려면 커서 설계 변경 필요
- **내 파티 목록 채팅방 누락 시 전체 오류** — 파티 생성과 같은 트랜잭션에서 채팅방을 만들고(`PartyService` 114행) 채팅방만 지우는 경로가 없어 현재 불변식상 발생 안 함
- **약관 동시 발행 ACTIVE 2건, 발행 중 OCI 확인 동안 트랜잭션 유지** — 관리자 1명 경로, 같은 버전 중복은 기존 검사가 막고 다른 버전 2개 동시 발행만 해당
- **탈퇴 정리 유저별 트랜잭션 분리** — 실패 관측 없음, 3번 알림으로 먼저 빈도 확인
- 프론트 변경 없음

## 성공 기준

- 1: 공개 GET에 만료·서명 불일치·형식 오류 토큰을 붙여도 200(인증 없는 요청과 같은 결과). 비공개 API는 기존처럼 401
- 2: `userUuid` 클레임이 UUID 형식이 아닌 토큰 → 401
- 3: 어떤 `@Scheduled` 작업이든 예외가 나면 Discord 운영 알림 1건 + 기존 오류 로그 유지
- 4: FCM 호출에 유한한 연결·읽기 타임아웃 적용. catch 안 기록이 실패해도 같은 배치의 나머지 항목 처리와 무효 토큰 비활성화가 계속됨
- 5: 같은 plan에 마커 교체 요청 2개가 겹쳐도 최종 마커는 한 요청분만 남음 (dockerTest로 검증)
- 6: 버전 쓰기 커밋 직후 `/check`가 새 값을 반환, 겹친 조회가 이전 값을 캐시에 다시 넣지 못함
- 7: 대상 메서드 13개가 src/main에서 제거되고 `./gradlew build`(detekt·Konsist 포함) 통과
- 전체 `./gradlew test`, `./gradlew dockerTest` 통과
