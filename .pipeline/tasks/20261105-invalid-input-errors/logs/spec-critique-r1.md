# Spec 비평 — 1차

- 대상: 승인된 `intent.md`, `spec.md`, `decisions.md`, `spec-changelog.md`
- 역할·범위: sub-designer의 spec 비평만 수행, 구현·티켓 작성·원본 문서 수정 없음
- 판단 근거: 제공된 문서와 지시서의 프로젝트 규칙만 사용, 저장소 구현 및 외부 자료 미탐색
- 분류: 아래 항목은 구현 결함 확정이 아닌 수용 기준·검증 계약의 보완 요청

### C-r1-01 교체 요청 실패의 기준을 기존 데이터 보존으로 명확화

- 관련: REQ-001, AT-001-2
- 근거: spec의 생성·교체 공통 수용 기준에 “400 INVALID_INPUT_VALUE, 마커·플랜 저장 0건” 명시
- 문제: 교체 API는 대상 플랜이 이미 존재하는 경로이며, 기존 마커가 있는 상태에서 전체 저장 건수 0을 기대하면 데이터 보존 요구와 충돌; 신규 저장 0건만 확인하면 기존 마커 삭제·변경을 놓치는 검증 공백
- 요청: 생성 실패는 요청 전후 플랜·마커 건수 변화 0, 교체 실패는 기존 플랜·마커가 있는 fixture에서 기존 행의 식별자·내용·개수 유지 및 신규 행 없음으로 분리
- 수용 확인: 열거된 위반 입력별 400과 요청 후 독립 조회 결과 검증; 교체의 빈 리스트 허용은 정상 요청으로서 기존 동작 유지
- 범위 판단: 신규 정책이 아닌 잘못된 입력의 무변경 처리 및 기존 데이터 보호 기준의 명확화

### C-r1-02 멱등 복구의 실제 HTTP 응답과 양쪽 생성 경로 회귀 검증 보완

- 관련: REQ-002·REQ-003, AT-002-2, AT-003-1·AT-003-2
- 근거: intent의 “각 항목 단위·통합 테스트” 및 비경합 DataIntegrityViolationException의 원래 응답 경로 유지; spec의 REQ-003은 단위 테스트 2개와 기존 PostIdempotencyIntegrationTest만 명시
- 문제: 원본 예외 인스턴스 재던짐은 단위 검증으로 적절하나, 실제 핸들러를 통한 404 오분류 방지의 통합 증거 부재; 플랜 경로의 같은 키·다른 바디 409 및 동시 같은 키·같은 바디 복구도 명시적인 통합 기준 부재
- 요청: 실제 컨트롤러·GlobalExceptionHandler를 통과하는 비경합 오류 통합 AT 추가, 게시글·플랜 각각 키 행 없음 + 미매핑 DataIntegrityViolationException → 500 및 404 아님 확인; 원본 인스턴스 동일성은 기존 단위 AT에서 유지
- 회귀 보완: 게시글·플랜 각각 같은 키·같은 바디 동시 요청의 단일 리소스 수렴 및 같은 키·다른 바디 409 IDEMPOTENCY_KEY_REUSED를 통합 검증; 기존 테스트가 담당하면 정확한 경로·테스트명·요구사항 매핑으로 대체
- 구현 제약: FK schema나 경합을 새로 설계할 필요 없이 생성 경계에서 오류 주입 가능, 복구 서비스와 HTTP 예외 처리 경로는 실제 동작 유지
- 범위 판단: 기존 멱등 동작 유지와 HTTP 오류 분류에 대한 승인 범위 내 검증 추가

### C-r1-03 Apple의 401 및 JWKS 장애 503을 검증할 통합 AT 명시

- 관련: REQ-004, AT-004-1
- 근거: intent의 Apple 누락 클레임 → 401 및 “각 항목 단위·통합 테스트”; spec의 JWKS 장애 → ExternalServiceException(503) 유지; 수용 테스트는 디코더 단위 AT-004-1만 존재
- 문제: 디코더의 InvalidJwtException만 검증하면 실제 인증 진입점의 예외 변환으로 인한 500 회귀 탐지 불가; 서명 검증을 앞으로 이동한 경로에서 JWKS 장애를 401로 삼키는 회귀도 현재 열거된 AT로 탐지 불가
- 요청: 실제 Apple 인증 진입점·verifier·decoder·예외 응답 경로를 통과하는 통합 AT 추가, 유효 서명 + exp/iat/sub 누락 및 blank sub → 401, 잘못된 서명 + 만료 exp → 401 확인
- 장애 보완: 메모리 JWKS source에서 키 공급 실패를 결정적으로 주입하여 ExternalServiceException 및 실제 HTTP 503 유지 확인; stale key로 정상 복구하는 경우와 구분, 네트워크 사용 금지 유지
- 입력 경계: 현재 입력에는 해당 인증 API fixture·테스트 파일 경로 부재; 메인 설계자가 제공할 정확한 진입점·참조 경로를 티켓 consumes에 명시, sub-designer의 저장소 추가 탐색 없이 전달
- 범위 판단: Google·Kakao 점검이나 JWKS 캐시 재설계 없이 승인된 Apple 오류 분류 검증만 보완

### C-r1-04 RED 회귀 증거와 전체 gate의 완료 기준을 spec에 연결

- 관련: REQ-001~REQ-004, 전체 AT
- 근거: intent 성공 기준에 “수정 되돌리면 새 테스트가 red” 및 ./gradlew build·./gradlew test 통과; 제공된 프로젝트 gate는 ./gradlew test build; spec에는 요구사항별 AT만 있고 회귀 RED 실행·기록 기준 부재
- 문제: 새 테스트의 GREEN만으로 원래 결함 탐지 여부를 입증할 수 없으며, 동작 유지 테스트는 수정 전에도 통과하므로 모든 테스트가 RED여야 한다고 해석할 위험
- 요청: 각 결함을 재현하는 지정 신규 AT에 대해 수정 전 실패 → 수정 후 통과 → 해당 수정만 되돌렸을 때 실패 → 수정 복원 후 통과의 증거 경로와 담당을 plan 또는 티켓에 명시; 기존 정상·경계·회귀 유지 테스트는 RED 대상과 구분
- 완료 기준: 동일 최종 구현 SHA에 연결된 ./gradlew test build 성공 출력과 요구사항별 RED/GREEN 증거, 미검증 항목은 별도 표시; 현재 비평 단계에서는 Gradle 실행 및 통과 주장 없음
- 범위 판단: 승인된 완료 기준의 추적성 보완, 추가 제품 기능·검증 정책 신설 없음
