# 프론트 전달 사항 — 재시도/중복 제출 방어 변경 (2026-08-04~05, PR #124~#126)

응답 유실 후 재시도, 더블탭 등으로 인한 중복 생성/중복 부작용을 막기 위한 백엔드 변경사항 정리. 대부분 **하위 호환** — 새 필드/헤더를 안 보내도 기존과 동일하게 동작하지만, 일부 항목은 프론트 반영이 필요.

---

## 1. `POST /posts`, `POST /plans` — `Idempotency-Key` 헤더 (신규, 선택)

모집글/여행계획 생성 요청에 재시도 시 중복 생성을 막을 수 있는 헤더가 추가됐습니다.

### 사용법

```
POST /api/v1/posts
Idempotency-Key: <클라이언트가 생성한 임의의 고유 문자열, 예: UUID>
Content-Type: application/json

{ ...기존과 동일한 요청 바디... }
```

- **버튼 한 번 누를 때마다 새 키를 생성**하고, 그 요청이 실패/타임아웃돼서 **재시도할 때는 같은 키를 재사용**하세요.
- 헤더를 안 보내면 기존과 완전히 동일하게 동작합니다(중복 방지 없음). **반영 안 해도 기존 동작 그대로 유지되지만, 재시도 중복 생성을 막으려면 프론트에서 헤더를 보내야 실제 효과가 있습니다.**

### 동작

| 상황 | 응답 |
|---|---|
| 키 없음 | 기존과 동일하게 생성 (`200 OK`) |
| 키 있음 + 최초 요청 | 정상 생성 (`200 OK`) |
| **같은 키 + 같은 바디**로 재요청 | 새로 만들지 않고, 최초 생성됐던 리소스를 그대로 `200 OK`로 재응답 (같은 `uuid`) |
| **같은 키 + 다른 바디**로 재요청 | `409 Conflict`, `errorCode: "IDEMPOTENCY_KEY_REUSED"` — 같은 키를 다른 내용으로 재사용하면 안 됩니다. 이 경우가 뜨면 새 키를 발급해서 새 요청으로 보내야 합니다. |

> 실제 성공 시 HTTP 상태 코드는 **`200`** 입니다(Swagger 문서상 201로 표기돼 있으나 실제 런타임 응답은 200 — 문서 오기, 추후 정정 예정).

### 참고: 재요청 응답의 `companionSpec` 필드 차이

같은 키로 재요청했을 때 응답의 `companionSpec` 필드가 최초 응답과 미묘하게 다를 수 있습니다 — 동행 조건을 안 보낸 경우, 최초 응답은 `"companionSpec": null`이지만 재시도 응답은 `"companionSpec": {"gender":[],"age":[],...}` (빈 배열들로 채워진 객체)로 옵니다. 기능적으로는 동일(둘 다 "조건 없음")하지만 **`companionSpec === null` 같은 엄격한 동등 비교를 하고 있다면 깨질 수 있으니**, `companionSpec`이 null이거나 모든 필드가 빈 배열인 경우를 동일하게 취급하도록 확인 부탁드립니다.

## 2. 채팅 메시지 전송(WebSocket) — `clientMessageId` 필드 (신규, 선택)

`/pub/chat/message`로 보내는 STOMP 메시지 페이로드에 필드가 하나 추가됐습니다.

```json
{
  "roomUuid": "...",
  "message": "안녕하세요",
  "clientMessageId": "클라이언트가 생성한 UUID (선택)"
}
```

- WS 재연결로 인해 ack를 못 받은 메시지를 클라이언트가 재전송하는 상황을 서버가 인식해서, **같은 `clientMessageId`로 이미 저장된 메시지가 있으면 조용히 무시**합니다(재저장도, 재알림도 없음).
- 안 보내면 기존과 동일 — dedup 안 됨(재전송 시 중복 메시지 생성될 수 있음, 기존 동작 그대로).
- **주의**: `/sub/chat/room/{roomUuid}` 구독으로 브로드캐스트되는 메시지 응답(`ChatMessageResponse`)에는 `clientMessageId`가 **포함되지 않습니다.** 낙관적 업데이트(optimistic UI)로 먼저 그려둔 로컬 메시지를 서버 브로드캐스트와 매칭시키려는 용도로 쓰신다면, `clientMessageId`가 아니라 다른 방식(예: 발신자 UUID + 본문 + 근접 시각)으로 매칭하셔야 합니다. 필요하시면 브로드캐스트 응답에도 이 필드를 포함시키는 후속 변경 요청해 주세요.

## 3. 파티 관련 액션 — 재시도 시 에러 대신 성공 처리

아래 액션들은 **"응답을 못 받아서 재시도했는데, 사실 첫 요청은 이미 서버에서 성공한 상태"**인 경우를 에러가 아니라 성공(`204 No Content`)으로 처리하도록 바뀌었습니다. 프론트가 별도로 대응할 건 없지만, **이제 이 상황에서 에러 토스트가 안 뜬다는 걸 인지**하고 계시면 됩니다.

| 액션 | 이미 목표 상태일 때(재시도) | 비고 |
|---|---|---|
| `POST /parties/{partyUuid}/join-requests` (가입 신청) | 이미 `PENDING`이면 → 새로 만들지 않고 기존 신청을 그대로 성공 응답(`201`, 동일한 `status: "PENDING"`) | ⚠️ 아래 참고 |
| `POST /parties/{partyUuid}/join-requests/{applicantUuid}/approve` (승인) | 이미 `JOINED`(승인됨)면 → `204` 성공 | |
| `POST /parties/{partyUuid}/join-requests/{applicantUuid}/reject` (거절) | 이미 `REJECTED`면 → `204` 성공 | |
| `POST /parties/{partyUuid}/members/{targetUserUuid}/ban` (강퇴) | 이미 `BANNED`면 → `204` 성공 | |
| `POST /parties/{partyUuid}/leave` (탈퇴) | 이미 `LEFT`면 → `204` 성공 | |
| `DELETE /parties/{partyUuid}` (삭제) | 이미 삭제된 경우 → `404`(기존과 동일, 단 에러 판정 순서만 바뀜) | 아래 참고 |

### ⚠️ 프론트 반영 필요: `PARTY_JOIN_ALREADY_PENDING` 에러 코드 제거

**가입 신청 중복 제출 시 나던 `PARTY_JOIN_ALREADY_PENDING`(400) 에러가 더 이상 발생하지 않습니다.** 이제는 신청이 이미 `PENDING` 상태여도 에러 없이 정상 응답(`201`)이 옵니다. 이 에러 코드로 분기 처리하는 로직(예: "이미 신청하셨습니다" 토스트)이 있다면 제거하거나, 프론트 자체적으로 중복 클릭 방지(버튼 잠금 등)로 대체해야 합니다 — 백엔드는 이제 이 케이스를 에러로 취급하지 않습니다.

### `DELETE /parties/{partyUuid}` 에러 우선순위 변경

이미 삭제된 파티에 대해 호스트가 아닌 사용자(또는 아예 관계 없는 사용자)가 재요청하면, 기존엔 `403`(권한 없음)이 먼저 떴는데 이제는 **`404`(파티 없음)가 우선**합니다. "이미 삭제됐다"가 실제 상황에 더 맞는 에러라 순서를 바꾼 것으로, 403/404 둘 다 이미 처리하고 계셨다면 별도 대응 불필요합니다.

## 4. 소셜 회원가입(`POST /auth/registration`) — 짧은 재시도는 성공 처리

응답을 못 받아서 회원가입을 재시도하는 경우(같은 소셜 계정으로 짧은 시간 내 재요청), 기존엔 `409 DUPLICATE_USER` 에러가 났지만 이제는 **최초 가입 후 30초 이내 재시도는 에러 없이 로그인 처리**됩니다(정상 가입 때와 동일한 토큰 응답).

- 30초가 지난 뒤 같은 소셜 계정으로 재가입 시도하면 기존과 동일하게 `409 DUPLICATE_USER`.
- 탈퇴한 계정으로 이 grace window 안에 재시도하면 `401 USER_WITHDRAWN`(신규 분기 — 기존엔 별도 처리 없었음, 필요시 별도 안내 메시지 고려해주세요).
- 프론트가 이 에러 코드로 "이미 가입된 계정입니다" 안내를 하고 있었다면, 이제 그 안내가 뜨는 타이밍이 "즉시 재시도"가 아니라 "30초 넘게 지난 뒤"로 좁혀졌다고 이해하시면 됩니다. 별도 코드 변경은 불필요.
