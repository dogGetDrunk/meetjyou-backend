# ADR-0004: 관광공사 여행지는 DB에 저장하지 않고 실시간 호출로 연동

**Status:** Accepted
**Date:** 2026-11-12
**Deciders:** damiannlee

## Context

- 여행지 검색(노션 작업 241) 데이터 출처 2개
  - 소상공인시장진흥공단 상가정보: 음식, 카페, 술집, 숙박, 쇼핑. 파일 데이터라 분기마다 DB 적재
  - 한국관광공사 국문 관광정보 서비스(`KorService2`): 관광지, 문화시설, 레포츠 약 1.9만 건
- 1차 구현(PR #280)은 두 출처를 같은 `place` 테이블에 넣는 전제로 설계
  - `place(source, source_key)` UNIQUE, 모집글과 파티와 여행계획서는 `place_id` FK로 참조(`V44`, `V46`)
  - 관광공사는 DB 저장에 '서버구축(DB저장) 방식' 승인이 필요해 1차에서 제외, "승인 후 적재기만 추가"하기로 함
- 2026-11-09 공사에 서버구축 방식 이용 의사 메일 발송, 11/12 공사 회신(신청서 양식과 조건)
  - 공사는 실시간 호출을 권고, **실시간으로 가능한 서비스면 반려**
  - 신청 사유에 DB 저장이 **기술적으로 꼭 필요한 이유**를 구체적으로 적어야 함
  - 검토 최소 5~7일 이상, 승인 전 대량 수집은 예고 없이 서비스키 차단 가능
  - 저장 후 동기화 책임은 신청자(국문 데이터는 매일 04:30, 07:30 갱신, 06:00 이후 동기화)
- 소상공인 운영 적재 현황(2026-11-22 운영 DB 조회): `SBIZ` 활성 1,023,599행, 관광공사 행 0

## Decision

- **관광공사 여행지는 실시간 호출, 소상공인은 기존 DB 검색 유지(혼합 방식)**
  - 관광공사: 키워드 검색, 지역 목록, 좌표 반경 조회를 요청 시점에 API 호출
  - 모집글, 파티, 여행계획서는 관광공사 장소의 `contentid` 만 저장
- 장소 참조에 관광공사 `contentid` 를 추가(후속 작업 244, 2026-11-26 개정)
  - `place_id` FK는 소상공인 전용으로 유지하고 `post`, `party`, `plan` 에 `tour_content_id VARCHAR(20)` 추가(`V48`~`V50`)
  - 한 행은 둘 중 하나만 가짐(CHECK `chk_<table>_single_place`)
  - 응답에는 `tourContentId` 만 내려주고 화면 이름은 기존 `location`(모집글), `destination`(파티, 계획서) 문자열 사용, 쓰기 시 형식(숫자 1~20자)만 검증하고 공사 API는 호출하지 않음
- 서버구축 방식 신청은 신청서를 제출하지 않고 철회

## 근거

- **반려 가능성이 높음**: 검색, 지역 필터, 지도 마커, 참조, 추천 집계 모두 실시간으로 가능. FK 참조와 DB 집계는 우리 설계 선택일 뿐 공사가 요구하는 "기술적 필수 사유"가 아님
- **얻는 것에 비해 대가가 큼**: 관광공사 1.9만 건은 소상공인 102만 건 대비 전체의 2% 미만. 이를 위해 승인 대기(5~7일+), 반려 위험, 매일 동기화 책임을 지는 것은 비효율

## Options Considered

### A. 실시간 혼합 방식 (채택)
- **Pros:** 승인 불필요, 동기화 책임 없음, 공사 데이터 최신성 그대로
- **Cons:**
  - 검색 결과가 관광지와 가게 두 묶음으로 나뉨(DB 쪽과 API 쪽 정렬과 페이지 통합 불가)
  - 관광공사 API 장애가 검색에 전파 → 장애 시 소상공인 결과만이라도 응답
  - 호출 한도가 검색 트래픽 상한이 됨(아래 리스크)
  - PR #280의 `place_id` 참조 모델 변경 필요. 단 운영 모집글 1건, 파티 1건, 여행계획서 0건 모두 `place_id` 미사용이라 이관할 데이터 없음(2026-11-22 조회)

### B. 서버구축(DB저장) 방식 신청 강행 (기각)
- 남는 신청 사유가 "통합 검색"과 "호출 한도"뿐이라 반박이 쉬움. 한도와 응답 속도는 실측하지 않은 상태
- 승인되더라도 매일 동기화 작업과 지연 책임이 추가됨

## Consequences / 알려진 리스크

- **호출 한도**(공공데이터포털 `15101578` 페이지, 2026-11-22 확인): 개발계정 **1,000**, 운영계정은 **"활용사례 등록시 신청하면 트래픽 증가 가능"** — 운영계정에 고정된 공개 한도가 없음
  - 서비스 런칭 후 운영계정을 별도 신청해야 함(공사 심사 5~7일, 상용 런칭과 공사 데이터 사용, 출처 표기 확인)
  - 런칭 전까지는 개발계정 한도 안에서 운영되므로, 검색 호출 수 측정과 한도 초과(오류 코드 22) 처리가 필요
- **출처 표기**: "출처 : ⓒ한국관광콘텐츠랩" 또는 "ⓒ한국관광공사", "TourAPI" 표기 금지
- **미확인**: 선택된 장소의 이름만 저장하는 것이 캐싱 금지에 해당하는지 공사에 문의 필요. 2026-11-26 개정 이후 이름은 저장하지 않고 화면 이름은 `location`/`destination` 문자열을 씀(조회마다 재조회는 호출 한도 때문에 기각). 공사가 이름 저장을 허용하면 이름 컬럼 추가를 별도로 결정

## 재검토 조건

- 운영계정 증설 한도가 실제 검색 트래픽을 감당하지 못할 때
- 관광공사 API 장애나 지연이 검색 품질 문제로 관측될 때
- 공사가 이름 저장을 허용할 때(이름 컬럼 추가 검토)

## 개정 이력

- **2026-11-26** (태스크 `20261126-place-ref-external-id`, 승인: damiannlee, 태스크 intent 승인)
  - Decision의 "장소 참조를 `place_id` FK에서 출처 + 외부 id 구조로 변경"을 "`place_id` 유지 + `tour_content_id` 추가, 둘 중 하나만"으로 정정
  - 기각: `place_source` + `place_ref` 로 통일. 출처가 늘어도 같은 구조를 쓸 수 있으나 소상공인 FK 무결성이 사라지고, `@ManyToOne` 대신 목록 응답 배치 로딩을 새로 짜야 해 동작 중인 소상공인 경로를 다시 손봄. 세 번째 출처 계획 없음
  - 기각: 조회마다 `detailCommon2` 로 이름 재조회(게시글 조회가 하루 호출 한도를 소모하고 공사 장애가 조회로 번짐), 쓰기 시 공사 API로 존재와 지역 확인(쓰기 경로가 외부 장애와 한도에 묶임)
  - 감수: 존재하지 않는 `contentid` 나 지역이 맞지 않는 값이 저장될 수 있음
  - 같은 개정으로 Consequences의 "미확인" 항목과 재검토 조건을 이 결정(이름 미저장, 재조회 없음)에 맞춤
